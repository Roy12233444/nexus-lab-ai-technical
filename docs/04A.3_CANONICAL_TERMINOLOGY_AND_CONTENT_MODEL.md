# 3. 🔬 Part II — Multi-Axis Epistemic State Taxonomy

To prevent oversimplified, misleading single-status labels, the Nexus technical website strictly decouples epistemic state into five orthogonal axes:

```text
                                 MULTI-AXIS TAXONOMY
                                          │
       ┌──────────────┬───────────────────┼───────────────────┬──────────────┐
       ▼              ▼                   ▼                   ▼              ▼
   1. MATURITY    2. EVIDENCE        3. TEMPORAL        4. RELATIONS    5. RELEVANCE
   • Conceptual   • Unknown          • Current          • Established   • Primary
   • Specified    • Documented       • Historical       • Proposed      • Supporting
   • Planned      • Reported         • Future           • Future        • Conditional
   • Implemented  • Observed         • Unknown          • Unknown       • Internal
   • Experimental • Verified                                            • Excluded
```

### 3.1 Maturity Axis (`MaturityState`)

- `CONCEPTUAL`: Idea or high-level direction documented without formal technical specification.
- `SPECIFIED`: Formal architecture, algorithms, and interfaces documented in engineering plans.
- `PLANNED`: Queued in official roadmap with scheduled implementation milestones.
- `IMPLEMENTED`: Physical codebase, modules, or test suites constructed.
- `EXPERIMENTAL`: Active laboratory testbed subject to iterative modification.

### 3.2 Evidence Axis (`EvidenceState`)

- `UNKNOWN`: No verification record or audit log currently attached.
- `DOCUMENTED`: Formally recorded in approved architectural specifications.
- `REPORTED`: Claimed in portfolio documentation; independent audit required.
- `OBSERVED`: Empirical output or execution logs captured during active runs.
- `VERIFIED`: Reproducible, passing test proof, soak run, or mathematical validation recorded.

### 3.3 Temporal Axis (`TemporalState`)

- `CURRENT`: Active organizational scope and priority in 2026.
- `HISTORICAL`: Past prototype, legacy project, or completed research cycle.
- `FUTURE`: Long-horizon exploratory target.
- `UNKNOWN`: Temporal context undetermined.

### 3.4 Relationship Types & States (`RelationshipType`, `RelationshipState`)

- **Types:** `DEPENDS_ON`, `INTEGRATES_WITH`, `INFORMS`, `RELATED_TO`, `DERIVED_FROM`.
- **States:** `ESTABLISHED` (proven by architecture/code), `PROPOSED` (planned integration), `FUTURE`, `UNKNOWN`.

### 3.5 Public Relevance Filter (`PublicRelevanceState`)

- `PRIMARY`: Core public surface on Overview (e.g., NALA, AMP, RTA-GUARD, COSMOS).
- `SUPPORTING`: Secondary contextual proof or deep-dive dossier.
- `CONDITIONAL`: Requires explicit maturity/evidence qualification before rendering.
- `INTERNAL`: Operational, governance, or proprietary internal record.
- `EXCLUDED`: Historical or deprecated artifact withheld from V1 public site.

# 4. 🏛️ Part III — Entity Model & Invariant Rules

### 4.1 Invariant Validation Rules

```text
[RULE-001] Complete Provenance: Every public claim must reference sourceId, authorityTier, and extractedAt.
[RULE-002] High-Tier Backing: Claims marked VERIFIED must be backed by Tier 1-3 authority.
[RULE-003] Temporal Boundary: Historical programs cannot be marked as PRIMARY public relevance.
[RULE-004] Proven Relationships: Relationships marked ESTABLISHED require an explicit evidenceRef.
[RULE-005] Evidence Verification: Programs marked VERIFIED must have verifiedMilestones populated.
[RULE-006] Program Isolation: Program-level maturity must remain distinct from component-level proofs.
```
