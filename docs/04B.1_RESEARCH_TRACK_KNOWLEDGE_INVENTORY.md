# 6. AMP Inventory

## 6.1 Identity

**Canonical identity:** AMP — **ANJANEYA Memory Protocol** — is a high-durability cognitive memory architecture focused on persistence, identity, retrieval behavior, compression, and memory survivability.

The AMP core document states the philosophical premise as: memory should be woven into identity rather than treated only as external storage. fileciteturn2file1L148-L161

The 04A.2 extraction identifies AMP as a memory architecture with persistent, holographic-memory and zero-null-retrieval objectives. fileciteturn6file0L40-L45

## 6.2 Problem

AMP addresses a family of memory-system problems:

- catastrophic memory loss;
- deterministic identity for stored memories;
- memory survival under storage loss;
- retrieval behavior that avoids an absolute “nothing found” result;
- memory salience / crystallization;
- adaptive compute allocation for retrieval;
- future temporal and associative reasoning.

The source document explicitly distinguishes the implemented Phase 1 persistence capability from the broader specified architecture. fileciteturn2file1L167-L182

## 6.3 Mission

The mission can be safely summarized as:

> Build a memory substrate in which important information can retain identity and survive severe storage loss, while providing a path toward richer retrieval, salience, compression, and adaptive memory behavior.

This is a synthesis of the documented pillars and implementation, not a claim that all pillars are complete.

## 6.4 Architecture

### Pillar inventory

| Pillar | Function | State |
|---|---|---|
| Chiranjeevi Persistence Layer | Memory survivability under catastrophic shard loss | BUILT & VERIFIED — Phase 1 |
| Dronagiri Holographic Compression | Retrieval/compression with no absolute null-result target | SPECIFIED |
| Devotion Crystallization | Importance / retention decision | IN PROGRESS |
| Sankat Mochan Retrieval | Retrieval/hallucination-defense concept | SPECIFIED |
| Anima-Mahima Adaptive Scaling | Adaptive compute for memory retrieval | SPECIFIED |
| TRIKALA | Associative + predictive memory | CONCEPT ONLY |

The pillar-status table is directly documented in the AMP core overview. fileciteturn2file1L167-L176

## 6.5 Components

### Phase 1 Chiranjeevi

The implemented subsystem contains:

- `param_hash.rs`
- `erasure.rs`
- `spore.rs`
- `substrate/mod.rs`
- `substrate/local_nvme.rs`

The implementation uses SHA3-256-derived deterministic identity and `(2,7)` Reed-Solomon erasure coding. The documented behavior is that any two of seven shards can reconstruct the original memory, permitting loss of five of seven shards. fileciteturn2file1L180-L198

### Cold-start / USHA

The project portfolio documents a cold-start design around a genesis substrate, provisional crystallization, and Anima-Mahima cold-start mode. fileciteturn4file7L1016-L1027

### Safety shell

AMP documentation defines a DHARMA Shell composed of:

- VARUNA Shield
- SHUDDHI Protocol
- VIVEKA Gate
- BRAHMA Constitution
- SATYA Layer

The source describes this layer as co-designed alongside AMP rather than added as a generic bolt-on. fileciteturn2file6L770-L780

## 6.6 Implementation

### Verified implementation

Phase 1 Chiranjeevi is the strongest AMP implementation evidence available.

The core document records that all five listed Rust components exist and that the test suite includes a destructive-recovery test: seven spores are stored, five are deleted, and the original memory is reconstructed from the two remaining shards. It records **66 passing tests**. fileciteturn2file1L180-L198

### Broader AMP implementation

The wider AMP program remains partial. The source states:

- `score.rs` exists for deterministic importance scoring;
- queue/allocator/freezer/registry work remains;
- Dronagiri, Sankat Mochan, and Anima-Mahima are specified but not implemented;
- TRIKALA is concept-stage only. fileciteturn2file6L801-L806

# 19. Research Track Knowledge Gaps

## Gap 1 — Program-level vs component-level maturity policy

NALA and AMP already demonstrate why this is required. A subsystem can be verified while the surrounding program remains partial. The canonical extraction preserves this distinction, but the website will eventually need a frozen vocabulary explaining it.

## Gap 2 — Independent verification boundary

NALA and AMP have stronger Tier-3 evidence. RTA-GUARD remains primarily Tier-5/Tier-7 for its key scale claims. A single evidence policy should define what counts as “verified” across all programs.

## Gap 3 — COSMOS implementation status

The accessible source plan says “Draft — Awaiting Implementation,” while other summary material calls the architecture comprehensive. The safe interpretation is “architecture documented; implementation pending,” but the current repository should eventually be inspected to determine whether later implementation artifacts supersede the draft plan.

## Gap 4 — Cross-program dependency semantics

Documented integration exists between NALA and AMP and between NALA and RTA-GUARD. The corresponding technical status for COSMOS remains relationship-level rather than dependency-level.

## Gap 5 — Evidence provenance at artifact level

The current source library often records the result of a test but not the full reproducibility package in the same document. For 04B.2, the preferred end state is a claim → artifact → execution record → reproduction method chain.

## Gap 6 — Public/internal evidence policy

The current materials identify public relevance candidates, but a final policy should specify exactly which classes of test artifacts may be public, which remain internal, and what additional review is required for security/IP-sensitive systems.
