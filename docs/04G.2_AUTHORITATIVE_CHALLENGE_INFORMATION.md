## 2. Core Domain Types (`src/types/challenge.ts`)

The domain type system establishes strict mathematical and structural bounds on all challenge data:

1. **`ChallengeId`**: Controlled union type (`'CH-001' | 'CH-002' | 'CH-003' | 'CH-004' | 'CH-005' | 'CH-006' | 'CH-007' | 'CH-008'`).
2. **`PressureDimension`**: Controlled union type (`'TIME' | 'UNCERTAINTY' | 'FAILURE' | 'SCALE' | 'RESOURCE_LIMITS' | 'RESPONSIBILITY' | 'ENVIRONMENT_SHIFT'`).
3. **`ChallengeEvidenceLevel`**: Controlled epistemic tiers (`'VERIFIED' | 'REPORTED' | 'DOCUMENTED' | 'EXPERIMENTAL' | 'THEORETICAL' | 'UNVERIFIED'`).
4. **`FailureMode`**: First-class entity containing `id`, `name`, and concrete `description`.
5. **`ResearchQuestion`**: First-class entity containing `id`, `question`, and `scope`.
6. **`ChallengeRecord`**: Complete profile containing technical dimensions, failure modes, research questions, negative non-claims, and evidence states.
7. **`ChallengeCrossTrackMapping`**: Relational bridge mapping each challenge to its corresponding Nexus Program, Philosophy Concept, and Future Direction.

## 4. Authoritative Selectors API (`src/content/challenge/challenge.ts`)

All downstream UI components and page blueprints access challenge data exclusively through controlled selectors:

- `getChallengeContent()`: Returns the full canonical content model.
- `getAllChallenges()`: Returns all 8 challenge records in strict chronological order (`CH-001` to `CH-008`).
- `getChallengeById(id: ChallengeId)`: Retrieves an individual challenge record.
- `getChallengesByPressureDimension(dimension: PressureDimension)`: Filters challenges by pressure vector.
- `getChallengesByEvidenceLevel(level: ChallengeEvidenceLevel)`: Filters challenges by epistemic evidence tier.
- `getPressureDimensions()`: Returns all 7 pressure dimension definitions.
- `getChallengeCrossTrackMappings()`: Returns all 8 cross-track structural links.
- `getGlobalChallengeNegativeBoundaries()`: Returns global negative boundaries.
- `getQuarantinedChallengeClaims()`: Returns quarantined claims for defensive rendering.

## 5. Machine-Enforceable Validation Engine (`src/lib/validation/challengeContentValidation.ts`)

The validation engine enforces 8 strict invariants:

- **`RULE-001 (ID Integrity)`**: All 8 canonical challenge IDs must exist with zero duplicate keys.
- **`RULE-002 (Canonical Completeness)`**: Exactly 8 challenge records must be registered.
- **`RULE-003 (Pressure Dimension Integrity)`**: All pressure vectors must match the 7 approved enum constants.
- **`RULE-004 (Evidence State Integrity)`**: Evidence levels must be valid and cannot be promoted without automated proofs.
- **`RULE-005 (Negative Boundary Invariant)`**: Every challenge must contain non-empty negative non-claims.
- **`RULE-006 (Failure Mode & Research Question Integrity)`**: Every challenge must specify structured failure modes and open research questions.
- **`RULE-007 (Cross-Track Integrity)`**: Mappings must cover all 8 challenges with valid programs, philosophy concepts, and future directions.
- **`RULE-008 (Marketing Firewall)`**: Rejects commercial marketing buzzwords (e.g. "guaranteed enterprise solution", "turnkey commercial product").
